This is an expert product audit, not a usability study. No participant session was conducted or supplied. Source inspection, automated browser checks, Axe, and reviewer judgment cannot establish beginner comprehension, assistive-technology usability, learning outcomes, or roadmap demand.

## Verdict

ORTUS has a credible live-model core. A person can technically launch a prepared system, run it, inspect model outputs, change a supported parameter or intervention, capture bounded summaries, and compare selected runs. The production Flocking shell makes the world primary without giving the renderer model authority.

The product does not yet support a complete scientific investigation lifecycle. Questions, reasons for a comparison, interpretation, counterevidence, and assessment are not provenance-bearing records. World summaries are browser-local comparison aids; Lab records nothing; Atlas results are page-local; Workshop drafts do not run. The result is a strong simulation workbench surrounded by several honest but weakly connected foundations.

Further atmosphere or scene treatment would not repair that break. The technical evidence provisionally favors observation/evidence infrastructure over I2. That direction remains provisional until actual participants test the comprehension hypotheses.

## Findings

### P0

None found in UR0. Core runtime tasks execute, and no current surface was found fabricating empirical validation or a generic runtime.

### P1

1. **Entry-point capability overclaim, fixed.** Start presented `Build a system` although Workshop cannot produce a runnable system, and said Lab could record something today although Lab records nothing. Start now says `Draft a model structure`, names it non-runnable, and describes Lab as a non-persistent foundation. Destination-purpose copy now says the same thing.
2. **Investigation continuity is absent, open roadmap gap.** ORTUS cannot preserve a scientific question, comparison rationale, evidence/counterevidence relationship, or assessment across World, Lab, and Atlas. Browser-local summaries and free-text notes are useful but are not an `Investigation`, `CanonicalObservation`, or evidence record. This blocks the mission's move from visual curiosity to durable investigation.
3. **Runnable remix continuity is absent, open roadmap gap.** Starters and Guides do not hand supported structure into a runnable remix path. Workshop starts a separate structural artifact and cannot execute it. Parameter changes provide bounded agency, but new mechanics still require source/template work.

### P2

1. Generic comparison requires substantial manual coordination: capture, launch another run, capture again, select runs, and set a baseline. The Guide reduces ambiguity for one pair but does not confer guide provenance on saved summaries.
2. Prominent `Worker runtime` language is technically accurate but adds implementation vocabulary to the primary World experience without helping a beginner answer a model question.
3. Atlas is a real but isolated Flocking-only tool; Lab is an honest foundation with little current task value. Grouping both with active comparison/experiment tools increases destination-role ambiguity.
4. Starter descriptions sometimes use `field` as ordinary spatial language even though ORTUS has no generic `SpatialFieldModel` runtime. Current boundaries prevent a direct support claim, but the terminology is needlessly collision-prone.
5. The evidence for Guides is one audited Flocking guide. General learning leverage, transfer, and educational outcomes remain unknown.

Comparison free text now says `Run notes` rather than `Observation notes`; the latter collided with ORTUS's reserved scientific-observation distinction.

| Distinction | Current technical support | Residual risk |
| --- | --- | --- |
| model != real system | Starter, Explain, metric, Guide, comparison, Lab, and Atlas copy state model scope. | Warning presence does not prove user understanding. |

| correlation/comparison != causation | Compare and Guide state this directly. | The UI lacks structured alternatives, counterevidence, or identifiability assessment. |

## Leverage Decisions

### Immersion

Further immersion is not the highest-leverage next branch. I1 already supplies a dominant, spatially present, inspectable Flocking world with bounded presentation state and Worker-owned execution. Current gaps concern question continuity, comparison meaning, evidence, and remix. Richer atmosphere would improve presentation while leaving those gaps intact. I2 should remain deferred unless participant evidence identifies scene comprehension or direct interaction as the dominant task blocker.

### Authoring

Authoring has substantial latent user-agency value, but current Workshop cannot create or remix a runnable system. S1/S2 could improve Starter-to-Workshop continuity and recipe-first comprehension. They must not be called executable authoring by themselves; generic execution still requires a later bounded runtime capability. Path B is a credible candidate, not the strongest answer to the current evidence gap.

### Observation And Evidence

O1/E1 address the largest technical break. ORTUS already produces identifiable run configurations, outputs, summaries, and exact continuation artifacts, but none is a scientific observation or investigation record. A narrow O1 contract can establish sampling, identity, loss, and provenance without reusing presentation channels. E1 can then organize questions, comparisons, counterevidence, and assessments without claiming empirical truth. This has higher scientific leverage than I2 and more direct leverage on the observed product loop than additional structural authoring alone.

## Human Study Protocol

### Purpose And Sample

Run a formative, non-representative study with approximately 5 to 8 participants when feasible:

- 2 beginners interested in complex systems;
- 1 to 2 domain scientists or technically literate researchers;
- 1 to 2 experienced modelers or technical product users;
- accessibility-focused participation or direct AT testing where available.

Use a clean browser profile and record the tested commit. Do not explain ORTUS architecture first. Do not collect names, account data, or identifying telemetry. A session identifier such as `UR0-P03` is enough.

### Session Shape

- 35 to 50 minutes.
- Think aloud where comfortable.
- Moderator observes before helping.
- Assistance is recorded with the exact task and reason.
- The moderator asks neutral follow-ups and does not teach the intended scientific distinction before the participant answers.

### Moderator Tasks

1. From Start, ask: `What do you think this product lets you do?`
2. Ask the participant to choose and launch a Starter World.
3. Ask them to determine what is happening and explain it in their own words.
4. Ask them to inspect one agent, group, or model-output readout without prescribing the control.
5. Ask them to change one thing intentionally and explain what changed, whether the active run reset, and what they expect to watch.
6. Ask them to create or use a comparison and identify what differs and what is held constant.
7. Ask for one conclusion the selected comparison supports inside the model.
8. Ask for one conclusion it does not establish about causation or the real world.
9. Trigger or request Reset/navigation, then ask whether this is still the prepared run and how they know.
10. Ask them to continue investigating, then explain the roles of World, Workshop, Lab, and Atlas in their own words.

Neutral probes include `What tells you that?`, `What would you do next?`, and `What do you expect this control to change?` Avoid `This is only a model, right?`, `Use Compare now`, or other prompts that supply the answer.

### Accessibility Variants

- Keyboard-only: complete launch, playback, inspection, change, comparison, Reset recovery, and destination navigation without a pointer.
- Screen reader: identify page purpose and current run, reach playback, inspect Canvas-adjacent state, hear validation/status changes, navigate comparison data, and verify modal focus return.
- Low vision/zoom: repeat the core World and Compare tasks at the participant's preferred zoom, including 200% where appropriate.
- Motion-sensitive: enable reduced motion and verify that no information or control disappears.

### Capture And Analysis

Use `UR0_STUDY_OBSERVATION_TEMPLATE.md` for each session. Record actions, hesitation, recovery, participant language, misconceptions, and assistance. Code comprehension only from what the participant says or does; do not infer it from task completion alone.

Synthesize recurring failure patterns, severe single-participant accessibility failures, differences by cohort, and contradictory observations. Do not treat 5 to 8 participants as statistically representative and do not invent pass thresholds after seeing results.

Layer B is sufficient for a final roadmap decision only when actual observations cover the core investigation loop, destination expectations, scientific distinctions, and recovery. It need not prove universal usability.
